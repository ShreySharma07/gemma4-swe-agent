# Strategy to Dec 2: why v14 fails half the tasks, and a fine-tuning plan that fits 4×L4 (Oct 27)

This note builds on `docs/handoff_20261027.md`. Its numbers come from v14's new-60 run (`data/runs/atul_eval_v14_new60/.../analysis/per_task.jsonl`) and v7's run on the same 60 tasks. The bucket split in §1 was computed for this note. Every rate is from one run, n = 60.

## 1. "If it solves 30, what stops it solving the other 30?"

The 30 failures fall into two populations that need different remedies. A task is **tractable** if its gold patch touches one file and ≤3 functions; otherwise it is **large**.

| Bucket | Tasks | v14 resolved | Failures |
|---|---|---|---|
| Tractable (1 file, ≤3 gold functions) | 41 | 26 (63%) | **15** |
| Large (≥2 files or ≥4 functions; up to 43 functions) | 19 | 4 (21%) | **15** |

**Large failures (15) are capacity failures.** The gold patches span 4–43 functions. Six of v14's 8 context overflows are in this bucket, and overflow tasks resolve 0/8. Thirteen of the 15 submit a partial or wrong patch. A4 showed that even completing them with gold edits rescues few (C6). With 28 calls and 32k tokens, these tasks are mostly out of reach for any prompt. They need a different scaffold (§3, idea F) or a model that wastes fewer tokens. Realistic headroom is about 2–4 tasks.

**Tractable failures (15) are budget and verification failures, not knowledge failures.**
- **12/15 used ≥27 calls**, so they hit the 28-call cap. Failed runs used a median of 28 calls, resolved runs 22. Time is not binding: failures took a median of 249 s, against a 480 s cap.
- **4/15 are empty patches.** Each saw the gold file, then spent 30–31 calls without editing.
- **9/15 left `repro.py` / `reproduce_issue.py` in the patch.** Of the 11 tasks with stray files, only 1 resolved. The agent writes a repro script, spends calls running and debugging it, and runs out of budget before verifying or cleaning up.
- **Verification is almost absent in every run.** A repro ran before the edit in 5% of runs, and tests ran after the last edit in 3.3% (2 runs, both resolved).
- Seven of the 15 saw the gold function and edited a different place ("saw gold, edited elsewhere").

So on tractable tasks the policy is *roughly right but inefficient*. It knows how to find the code, but it uses its calls on ad-hoc scripts and runs out before it commits or verifies.

**Headroom estimate:** recovering 6–8 of the 15 tractable failures plus 2 large ones would give 38–40/60. That is what separates us from the 0.24 teams.

**Cheap tests these numbers suggest (no training):**
1. **`max_tool_calls` 28 → 40, everything else unchanged.** With thinking on, calls are more deliberate than in v9's thinking-off test, which did not help. Worst-case runtime is unchanged because the 8-min time cap still binds. Risk: more overflows.
2. **CPU re-grade without stray files.** Strip non-source files from the 11 stray-file patches and re-grade them. If any pass, a cleanup rule is a free win. If none pass, the stray files are only a symptom of running out of budget.
3. **"Repro in one call" rule.** Use `python -c` only and never write repro files. v17's prompt already says "never create a file". The v17 run (pushed Oct 27, `shreysharma07/gemma4-eval-v17-new60`) will show whether that alone removes the stray files.

## 2. Why our fine-tuning failed (diagnosis in the field's terms)

| Run | What we did | Failure mode | Lesson |
|---|---|---|---|
| Step C/D | SFT on another agent's (OpenHands/Qwen) trajectories, reasoning stripped, mid-run windows | **Off-policy imitation** with exposure bias: the model learned rituals (README → pytest loop), solved 0/114 | Train only on states the model itself visits |
| S3 / S3b | SFT on compressed teacher episodes | **Action-frequency shift**: pytest at ~19% of calls compounded into loops over a rollout | Each data distribution has a frequency signature; single-step gates miss it |
| S1 | Own v7 solved runs, thinking OFF | Behaviour neutral or worse, and the data is now in the wrong mode | Thinking ON is the serving mode, so the data must match |
| All | ≤8k-token windows | The model is served up to 32k, so late-run decisions (commit, verify, submit) were never trained in their real context | Decisions late in a run are exactly where tractable tasks fail (§1) |

The common cause is that **we trained on states and contexts the deployed policy never sees.** Every plan below is on-policy, uses thinking-ON data, and supervises late-run decisions in their full context.

## 3. Fine-tuning plan that fits 4×L4

The constraints: 30 GPU-h/week per account (2 accounts, billed at 2×), training proven only at ≤8k tokens per sequence, LoRA rank ≤128, ≤8 adapters, and adapters routable per sub-agent.

### A. Remove the 8k limit: prefix-cached truncated backprop (engineering, ~1 GPU-h probe)
- Run the first *P* tokens of a trajectory (up to ~24k) **under `torch.no_grad()`** and keep only the KV cache, detached.
- Then run forward and backward on the last ≤8k tokens, attending to that cache.
- Memory cost: activations for 8k tokens plus a KV cache for 24k. Most Gemma-4 layers use sliding-window attention, so their cache is bounded; only the global layers grow with *P*.
- The LoRA weights still shape the prefix through its forward pass, but gradients do not flow back through it. This is the standard truncated-BPTT approximation.
- **Result: we can supervise call 20–28 decisions (commit, verify, clean up, submit) in their real 20–30k context.** The probe should measure peak memory at P = 16k and 24k, and whether the KV cache can be sharded the same way the layers are split.

### B. Task factory: verifiable, never-seen tasks with no environment work (SWE-smith-lite, CPU)
- **The bottleneck for on-policy training is tasks we can grade offline.** SWE-rebench repos need environment builds. Instead, mutate **pure-Python libraries that are already installed and testable in the scorer environment**: the wheelhouse and image packages, such as click, attrs, httpx, starlette, pydantic-core-free packages, jinja2, markupsafe and more-itertools. Exclude fastapi, rich and requests to avoid public-LB leakage and memorisation.
- Procedure:
  1. Pick a function covered by tests.
  2. Inject a bug: an AST mutation (flipped condition, off-by-one, dropped branch, wrong default, swallowed exception), or a model rewrite ("introduce a subtle bug").
  3. Keep the tests that now fail (fail-to-pass) and check that the rest still pass (pass-to-pass).
  4. Have Gemma write an issue from the failing test and its traceback, and **remove the test code from the issue text.**
- Add **multi-function bugs**, by mutating 2–3 related functions together, to train for the large bucket.
- Cost: CPU kernels only. The target is **1,000+ tasks across 15–30 repos.** The gold patch is the reverse of each mutation, so a solved/failed label is exact.
- Because these repos look like neither the public 129 nor (probably) the hidden ones, the factory also lets us **measure memorisation-free generalisation** (CLAUDE.md's open problem) at no extra cost.

### C. On-policy rollouts at 4–8× throughput
- The official `Evaluator` accepts `concurrency`. Our runner uses 1 for fidelity to the scorer, but **for data generation, concurrency 6–8** lets vLLM batch requests, giving an estimated 3–5× more tasks per GPU-hour (to verify in the first run).
- Generate with v17 (thinking ON, the serving prompt), using k = 2–4 samples on the tasks it sometimes solves. About 600 rollouts should take ~2 sessions.
- Keep the full trajectories, including thinking, labelled by hidden-test outcome.

### D. Three adapters, each a narrow and safe learning problem

1. **Verifier/critic adapter.** Given the issue and the final `git diff`, plus optionally the last test output, it predicts pass or fail and gives a one-line reason.
   - This is outcome-reward modelling, the method behind the biggest best-of-N gains on SWE-bench (SWE-Gym's verifier, CodeMonkeys).
   - It is much easier to learn than a policy, and the labels already exist: ~270 v7×5 patches, v7, v14, v16 and S3b on new-60, plus the factory rollouts.
   - Inputs fit in 8k, so no new training infrastructure is needed.
   - **Gate:** AUROC on held-out repos ≥ 0.75 before it is wired into any agent.
2. **Policy RFT adapter (ReST/STaR, own policy, thinking on).**
   - Train on successful factory rollouts. Prefer the shortest successful run per task, which selects for call-efficiency (§1's binding constraint).
   - Use idea A so that late-run commit, verify and clean-up decisions are supervised.
   - Keep the dose low (lr 5e-5, 1 epoch) and use rank 16–32.
   - **Gate:** an 8-task rollout check of action-frequency drift, then paired new-60.
3. **Step-level preference adapter (optional, after 2).**
   - Find pairs of the model's own rollouts on the same task that share a prefix and diverge: one solves, one fails.
   - At the divergence point, train DPO/KTO with the solved action as preferred.
   - The KL-anchored objective drifts less than SFT, which addresses the S3 fixed-script failure. This targets the "kept exploring instead of editing" and "edited elsewhere" decisions.

### E. Using the verifier in the declarative agent (no Python entry point needed)
Build a `SequentialAgent`/`LoopAgent` with these stages:
1. **Fixer**: the base model, v17 prompt, about 20 calls.
2. **Critic sub-agent** on the verifier adapter (`include_contents: none`): it reads the issue and the `git diff` and writes a verdict to state through `output_key`.
3. **Repair stage**: runs only if the verdict is *fail*. It starts from the existing diff with the critic's reason, with about 8 calls and fresh context through `{critic_verdict}`.

The fresh-context repair also helps the overflow tasks, since the repair stage does not inherit 25k tokens of history.

### F. For the large bucket: plan-then-execute with checkpointed state
1. A planner sub-agent lists every site to change, using BM25-style `git grep` on the shared identifiers (C10/C11: co-changes share identifiers and are found lexically) and writes the list to state.
2. Executor passes, each with fresh context, edit 2–3 sites at a time.

This attacks overflow directly. It needs no training, but trained adapters could later specialise the planner.
